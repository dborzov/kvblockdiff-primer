Every decode step, at every layer, about 274 entries miss the [[hot-cache]] in the reference setting ([[#landscape-derived-numbers]]). A request's 100K tokens fall into 25 [[block|blocks]] of 4,096. The GPU keeps the dictionaries of only a few blocks — say $\vnD = 4$ — on its [[dictionary-cache]]. Where do the 274 misses land?

Here are two worlds with the same miss count. The delta ratio is an assumed $\vrho = 0.65$.

| | misses spread evenly | misses piled into 4 heavy blocks |
|---|---|---|
| misses per layer per step | 274 | 274 |
| blocks they land in | all 25 | mostly the same 4 |
| δ-miss fraction $\vfD$ with 4 dictionaries resident | 4 / 25 = 16 % | 85 % (assumed) |
| link bytes, in raw entries' worth | 274 × (0.16 × 0.65 + 0.84) ≈ 259 | 274 × (0.85 × 0.65 + 0.15) ≈ 192 |
| saving on miss traffic | about 6 % | about 30 % |

Here are both worlds, miss by miss. The first view counts the misses in each block; the second puts every miss at its place in the request.

The count is the same, and so is everything the hot cache knows. In the even world only 44 of the misses happen to fall where a dictionary waits; in the piled world 233 do. Same data, same coder, same $\vrho$. The only difference is *where the misses land*, and it is worth five times more saving.

::: aside reminder δ-misses and raw misses
A [[delta-miss]] lands in a block whose dictionary is resident, so only the delta ($\vrho\,\ve$ bytes) crosses the link. A [[raw-miss]] lands in a cold block and moves the whole entry. The share of δ-misses is $\vfD$ ([[#idea-blockdiff-step-by-step]]).
:::

## The question, in one sentence {#question}

::: note key Q3 in one line
Does the indexer's habit of re-selecting the same entries also pile the misses into a few blocks, and do those blocks stay heavy for many steps?
:::

Spelled out, it has three parts, each feeding the next.

1. **At what block size** do selections and misses cluster into a few [[heavy-block|heavy blocks]]? Small blocks split one hot region over several blocks; big blocks cluster easily, but give each dictionary a wider, less alike stretch of tokens to fit.
2. **For how long** does a block stay heavy? This is the block's own reuse distance: how many steps pass before a block comes back.
3. **Therefore**: how many dictionaries must be resident ($\vnD$), and how often must a new one be loaded ($\vnload$ per step per layer)?

Part 2 is the trap of the table above. The right-hand column assumed that the same 4 blocks stay heavy. If they changed every step, each change would load a dictionary of $\vw$ entries' worth. With a heavy dictionary, $\vw = 256$, one load costs about as much as all 274 misses of that step. So loads must be rare:

$$
\underbrace{\vnload \, \vw}_{\text{dictionary traffic}} \ll \underbrace{274}_{\text{misses per layer per step}}
$$ {#eq-questions-load-budget}

For $\vw = 256$ that means fewer than about 0.1 loads per step per layer: each dictionary must stay useful for well over ten steps. For $\vw = 32$, up to about one load per step is fine ([[#homework-break-even]]).

::: takeaway
- Q3: do misses pile into few blocks, and do those blocks stay heavy for many steps?
- Where misses land can change the saving several-fold at the same $\vrho$.
- Loads must be rare: $\vnload\,\vw \ll 274$.
:::

## What yes, no and partly would look like {#outcomes}

Framework C ([[#questions-framework-c]]) replays the indexer's selections and reads off $\vfD$ and $\vnload$ for every $\vnD$ and $\vb$. The outcomes, written down now:

| answer | what replay shows | what we would do |
|---|---|---|
| **yes** | $\vfD \ge 0.8$ with $\vnD \le 8$, and $\vnload \le 0.1$ | heavy block dictionaries are affordable; the full design with a dictionary cache |
| **partly** | $\vfD$ between 0.5 and 0.8, or heavy blocks that change often | only light dictionaries, or a few heavy ones for the heaviest blocks; the cost model decides |
| **no** | $\vfD < 0.5$: misses spread over many blocks | heavy block dictionaries are out; use light ones resident for every block, or one per request |

::: note intuition Q3 only matters if the dictionaries are heavy
A light [[loc]] dictionary weighs $\vw \approx 2$ entries. All 25 of a request's block dictionaries together weigh about 50 entries per layer — under 2 % of a 4,096-slot hot cache. They can simply all stay resident, and $\vfD = 1$ by construction ([[#missed-light-dictionaries-first]]). So Q3 becomes urgent only if wave 1 finds that heavy dictionaries are needed.
:::

::: takeaway
- Yes: $\vfD \ge 0.8$ at $\vnD \le 8$ with $\vnload \le 0.1$. No: $\vfD < 0.5$.
- A "no" rules out heavy block dictionaries, not the project.
- With light dictionaries, Q3 is moot: everything is resident.
:::

## Where Q3 plugs in {#links}

Q3 is the [[lucky-louis]] seen at block granularity. Lucky Louis says the indexer re-selects mostly the same *entries* from step to step, which is why a small hot cache hits. Q3 asks whether those entries also crowd into the same *blocks* — the [[heavy-block]] property of [[#idea-heavy-blocks]].

::: theme which-vs-what
Q3 is entirely a "which" question. It can be answered from a trace of selected positions without opening a single entry. That also makes it independent of Q1, which is entirely about "what".
:::

Because the two are independent, all four combinations are possible, and each points at a different system.

| | Q3 yes: heavy, long-lived blocks | Q3 no: misses spread |
|---|---|---|
| **Q1 yes, at block scale** | the full design: block dictionaries and a dictionary cache | light block dictionaries, all resident; heavy ones are out |
| **Q1 yes, at request scale only** | one dictionary per request; Q3 is moot | one dictionary per request |
| **Q1 no** | nothing worth caching | solo coding on the miss path |

The levers care too. A dictionary cache serves [[lever]] 1 only for misses in resident blocks, and lever 2 — deltas inside the hot cache — can only compress entries whose dictionary is at hand. Framework D ([[#questions-framework-d]]) turns $\vfD$ and $\vnload$ into requests per GPU.

::: takeaway
- Q3 is Lucky Louis at block granularity: a statement about which entries, never about their bytes.
- It is independent of Q1; the four combinations point to four different systems.
- Its answer feeds the cost model through $\vfD$ and $\vnload$.
:::
