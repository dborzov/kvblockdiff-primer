a primer & a research proposal

kvblockdiff

Small, similar things refuse to compress one at a time, unless the receiver already knows what they usually look like. A primer, a clean statement of one compression problem, the measurements so far, and the plan, for the working memory of an LLM.

Begin with a story Back to school first

A weather station on a lonely rock sends the mainland a short message every half hour. Each message is almost identical to the one before it, yet compressing any one of them on its own saves almost nothing. The fix is old and clever: agree on a dictionary in advance, and from then on send only what is new.

An LLM has the same problem at a much bigger scale. While it writes, it keeps everything it has read in a growing store of keys and values, its orchard. Sparse-attention LLMs keep that orchard in the computer’s main memory and fetch small pieces of it to the GPU at every step, thousands of tiny fetches per word. This site asks one question: could those pieces travel as short deltas against a shared dictionary, and come back bit for bit identical?

The question has a clean core, the compression scenario of Part IV: a sender holds the orchard, a receiver asks for one cherry at a time, a dictionary is shared in advance, and every cherry must come back exactly. Two autonomous research campaigns ran that scenario through a harness on real Qwen3.5-2B orchards (Part VIII). The plan for what to measure next is Part X.

What this is, and what it is not

In scope: how the orchard of a long sequence is stored in host memory and moved to the GPU during sparse-attention decoding, with the LLM’s outputs unchanged, bit for bit. Everything here is lossless.

Out of scope: anything that changes what the LLM computes: no approximate (lossy) compression of the orchard, no dropping tokens, no retraining. There is a large literature on lossy orchards; it shares keywords with this project and solves a different problem. We read it only for hints about where structure lives (Part IX).

The LLM never notices. Only the bytes on the link get smaller, if the orchard is as alike as we hope.

The cast

The signature ideas of this project each have a name, an emblem and a colour. When you meet one in the text it looks like this, and hovering it brings back its reminder.

dictionary “the Almanac” Bytes shared by many cherries and held by the receiver before it asks for any of them, so that each cherry can be sent as a short delta. A zstd trained dictionary, a codebook, furrow statistics and a set of reference cherries are all dictionaries. Not a Python dict. delta “the Remainder” The bytes sent for one cherry; with the dictionary they rebuild it bit for bit. Its size over the cherry’s raw size is the delta share, ρ. kvblockdiff “the Delta Store” Serve the indexer’s picks as deltas against punnet dictionaries kept on the GPU, so that a hot-cache miss moves a delta instead of a raw pick and the GPU rebuilds it bit for bit. One spelling, no hyphen. orchard “the Orchard” Every key and every value of one sequence at every KV layer, kept in host memory: two arrays k, v of shape (n_tokens, n_kv_layers, n_kv_heads, head_dim). It grows one row per token and is never pruned. A store, not a cache, whatever its usual name suggests. furrow “the Furrow” One fixed elem_id, read across many vectors: v[:, layer_id, head_id, elem_id] in the orchard, one sensor’s column in a table of readings. Per-furrow statistics are a location and a scale for each element position. pick “the Pick” One (layer_id, token_pos_id) the indexer selects at one decode step: the unit the hot cache holds and a miss fetches. What a pick covers depends on the LLM (one layer in DSA, a group of layers in GLM-5.1). A pick is served with one or more cherries. stretch “the Stretch” stretch_len consecutive token positions of one sequence; stretch_id = token_pos_id // stretch_len. A knob we choose, not a fact of the data, and it says nothing about which tensor coordinates are in play. slice “the Slice” The rule naming which part of the orchard a scenario compresses: keys or values or both, which layers, which heads, which elements; written as the Python slice it is, e.g. v[:, [1, 3], 0, :]. cherry “the Cherry” The unit the receiver asks for and the sender answers with one delta: the chosen vectors of one token position of the slice, written as an index expression with its element count, e.g. cherry(t) = v[t, l, :, :], 512 elements, cherry_bytes == 512. Every cherry of a scenario has the same size, known to both sides in advance; cherries that stack several positions are out of scope. punnet “the Punnet” All cherries of one stretch under one slice and one cherry shape: what one compress call sees and what one dictionary serves. punnet_size cherries. Not an orchard and not a stretch. leash “the Leash” Rebuilding any one cherry from cold may read at most leash × cherry_bytes distinct bytes of the dictionary, counted in the scenario’s own cherry and checked for every cherry. One leash per stretch length: 137 at 512 positions, 293 at 4096, 1103 at 16 384, 14 503 for the whole sequence. It keeps “compress the whole punnet as one stream” out of the game. compressor “the Press” One concrete pair of functions, deltas, dictionary = compress(punnet) and decompress(delta, dictionary), built as a dataflow graph of stages. The campaigns wrote 126 of them. hot cache “the Hearth” HiSparse’s small buffer of B raw picks per sequence per layer, kept in GPU memory and managed least-recently-used. Picks found there are hits; the rest are misses fetched from host memory over the link. dictionary shelf “the Bookshelf” kvblockdiff’s per-layer set of nD​ punnet dictionaries kept in GPU memory, one per stretch that is on fire. A miss in a stretch whose dictionary is on the shelf can be served by a delta. δ-miss “the Feather” A hot-cache miss whose stretch’s dictionary is on the shelf, so only the delta (ρe bytes) crosses the link and the GPU rebuilds the pick. raw miss “the Crate” A hot-cache miss whose stretch’s dictionary is not on the shelf, so the full raw pick (e bytes) crosses the link, exactly as in HiSparse today. heavy stretch “the Anvil” A stretch that holds many of the current step’s picks. If picks pile into a few heavy stretches for many steps, keeping their dictionaries on the shelf is cheap. victim tier “the Lifebuoy” A second GPU tier holding the deltas of picks just evicted from the hot cache. If one of them is picked again it is rebuilt on the GPU instead of being fetched over the link. the Pin “the Pin” One of the two frozen rigs every estimate is quoted for: HiSparse’s GLM-5.1 deployment at 8-bit storage: 78 sparse layers, 2048 picks per layer per step, 100K-token context, 640-byte cherries, 30 ms per token, a 50 GB/s link, 30 GB of GPU memory for orchards. the Bench “the Bench” The second frozen rig: Qwen3.5-2B’s six KV layers, 2 heads × 256, 512-byte cherries for one token’s values at one layer, 225K-token coding-agent transcripts, FP8, on one RTX 5080 with a 50 GB/s link. No indexer ran on it, so picks, misses and step time are not measured there. HiSparse “the Two-tier Library” The serving system we build on. It keeps each sequence’s orchard in host memory and a small least-recently-used hot cache of raw picks per layer on the GPU. The LLM’s outputs are unchanged. indexer “the Scout” A cheap scorer that, at every layer and every decode step, looks over all past positions and names the k picks attention will read. Its picks are announced before any bytes of the orchard are touched. Lucky Louis property “the Gambler” From one decode step to the next, the indexer re-picks mostly the same positions, so a cache that bets on last round’s winners keeps winning. It is about WHICH picks are wanted, not about their bytes. neighbour similarity “the Neighbours” The family of hypotheses that a cherry costs fewer bits to store exactly when a neighbouring cherry along some axis of the orchard is already known. Members: fallen-apple (token axis), upstairs (layer axis), stereo (head axis), echo (repeats). fallen-apple similarity “the Apple” Hypothesis: a cherry is cheaper to store exactly given a cherry of the same layer a small token distance Δ away, and the closer the neighbour the cheaper. A curve over Δ, not a threshold. Measured: weak, except in the middle layers. upstairs similarity “the Staircase” Hypothesis: the cherry of the same token one layer up is partly predictable from the one below it. Measured: small, and by kind of layer rather than by adjacency. stereo similarity “the Stereo Pair” The two KV heads of a layer at one token are two views of one vector: their elements have a cosine near zero, yet joining them into one cherry saves about 0.85 bit per element. The strongest structure the campaigns measured. echo similarity “the Echo” An earlier occurrence of the same token, however far away, predicts a cherry far better than its neighbours do. Reference trees live on echoes; in the data the axis that mattered was repetition, not distance. cat-sequence ladder “the Ladder” The intuitive argument for the project: a cherry is less surprising against its own sequence than against everything, and least surprising against its own neighbourhood. Right in direction, leaky in its evidence, and harsh in its exchange rate. solo “the Hermit” Coding each cherry by itself with one fixed, context-free table (per-furrow histograms fit once on a calibration corpus). 0.778 on the Bench’s values. The baseline every dictionary must beat. furrow statistics “the Anchor” The lightest dictionary: for each furrow, a typical value (location) and a spread (scale). Predict each element by its furrow’s location; store the exact difference. Weighs about two cherries, no per-cherry tax. KLT “the Compass” The rotation of the axes that lines them up with the directions in which the data spreads most (the same thing as PCA). After it, the coordinates are uncorrelated and can be coded one by one with no loss of efficiency. VQ “the Hive” Describe each vector by the index of the nearest of C reference vectors (centroids) in a codebook. Losslessly, the index is a prediction and the exact residual is stored too; the index costs log2​C bits per vector. sibling “the Twin” Use another cherry of the same punnet (the nearest “sibling”) as the prediction, plus a pointer to it. Cheap side information, but the residual is the difference of two noisy vectors, so its noise doubles. The reference tree is its grown-up form. global scope “the Globe” A dictionary fit once, offline, on a calibration corpus and shared by every sequence. Free at serving time; captures only what all texts have in common. sequence scope “the Spool” A dictionary fit on one sequence’s own slice, loaded once when the sequence is admitted. Captures what is special about this conversation. The same as stretch scope with one stretch as long as the sequence. stretch scope “the Brick” A dictionary per punnet, fit on the punnet itself. Fits the local neighbourhood best, but there are many of them per sequence and the ones in use must be on the GPU. compressibility curve “the Arch” For one compressor on one scenario, the points (delta share, dictionary share) of its configurations. What is read off it is the point of lowest MDL ratio and the split it falls at; the lowest ratio over all compressors is the roofline.

Running themes

A handful of ideas come back again and again. Each time one does, a dashed card marks it and lists every other place it appears.

Predict, then store only the surprise Every lossless compressor in this story has the same shape: guess the next thing from what both sides already know, then store only how wrong the guess was. The better the guess, the fewer bits. Side information at both ends A message gets cheaper when the receiver already knows something relevant: an almanac, a trained dictionary, a punnet's statistics sitting on the GPU. The catch is that the receiver must really have it. Pay once, use many times A fixed cost (a dictionary, a codebook, a calibration) is worth paying only when it is shared by enough cherries. Per cherry it costs (fixed cost) ÷ (number of cherries). The access pattern decides the form How data is read, one big stream or many tiny scattered asks, decides what a compressor is allowed to look like, before any statistics are considered. The leash is this theme written as a rule. Which picks, versus what is inside them Knowing which picks will be wanted (a property of the indexer) is a different thing from the cherries being alike (a property of their bytes). Evidence for one is not evidence for the other. Bits are the unit Surprise, redundancy, mutual information and compressed size are all measured in bits, and bits × cherry size = bytes on the link. Similarity scores that do not convert to bits do not count. Lossless pays for all the noise A lossless compressor must reproduce every last bit, including the parts that are pure noise. Whatever no predictor can explain sets a floor that no clever dictionary can go below. Every helper charges a tax Each piece of side information costs something to store or send: index bits, dictionary bytes, escape lists, flags. A stage wins only if its gain is larger than its tax. Trust, but shuffle A measurement is believable only with controls that would expose a mistake: shuffled data where the effect must vanish, synthetic data with a known answer, and a real round trip that must be exact. The number grid is not neutral How numbers are stored (a uniform integer grid or a logarithmic floating-point grid) changes which tricks work. The same prediction can save bits on one grid and lose bits on another.
