a primer & a research proposal

kv-blockdiff

Small, similar things refuse to compress one at a time — unless the receiver already knows what they usually look like. A story, a primer, and a research proposal about doing exactly that for the working memory of a language model.

Begin with a story Back to school first

A weather station on a lonely rock sends the mainland a short message every half hour. Each message is almost identical to the one before it, yet compressing any one of them on its own saves almost nothing. The fix is old and clever: agree on a dictionary in advance, and from then on send only what is new.

A large language model has the same problem, at a much bigger scale. While it writes, it keeps a working memory of everything it has read — its KV cache. Modern models with sparse attention keep that memory in the computer’s main memory and fetch small pieces of it to the GPU at every step, thousands of tiny fetches per word. This site asks one question: could those tiny pieces travel as short deltas against a shared dictionary — and come back bit for bit identical?

The answer depends on one property of KV caches that nobody has measured yet. The site names that property, does the homework around it, and plans a weekend-sized first experiment.

What this is, and what it is not

In scope: how the KV history of a long conversation is stored in host memory and moved to the GPU during sparse-attention decoding — with the model’s outputs unchanged, bit for bit. Everything here is lossless.

Out of scope: anything that changes what the model computes — no approximate (lossy) compression of the cache, no dropping tokens, no retraining. There is a large literature on lossy KV compression; it shares keywords with this project and solves a different problem. We read it only for hints about where structure lives (Part V).

The model never notices. Only the bytes on the wire get smaller — if the KV cache is as alike as we hope.

The cast

The signature ideas of this project each have a name, an emblem and a colour. When you meet one in the text it looks like this, and hovering it brings back its reminder.

dictionary “the Almanac” Information shared by many items and sent to the receiver once, so that each item can be sent as a short delta instead. A zstd trained dictionary, a codebook and a set of per-channel means are all dictionaries. delta “the Remainder” The bytes needed to rebuild one item exactly, given its dictionary. For a KV entry, its size is ∣δ∣=ρe. kv-blockdiff “the Delta Store” Store a long KV history as per-block dictionaries plus tiny per-entry deltas, so that a cache miss moves a delta instead of a raw entry and the GPU rebuilds the entry bit for bit. entry “the Tile” All the key and value numbers of one token at one layer, El,t​, of size e bytes. The unit the indexer selects, the cache moves and our coder must rebuild. block “the Row” b consecutive tokens’ entries of one request at one layer. A design knob of the algorithm (we choose b), not a property of the data. hot cache “the Hearth” HiSparse’s small buffer of B raw entries per request per layer, kept in GPU memory and managed least-recently-used. Entries found there are hits; the rest are misses fetched from host memory. dictionary cache “the Bookshelf” kv-blockdiff’s per-layer set of nD​ block dictionaries kept in GPU memory. A miss in a block whose dictionary is on this shelf can be served by a delta. δ-miss “the Feather” A hot-cache miss whose block dictionary is resident, so only the delta (ρe bytes) crosses the link and the GPU rebuilds the entry. raw miss “the Crate” A hot-cache miss whose block dictionary is not resident, so the full raw entry (e bytes) crosses the link, exactly as in HiSparse today. heavy block “the Anvil” A block that holds many of the current step’s selections. If selections pile into a few heavy blocks for many steps, keeping their dictionaries on the GPU is cheap. victim tier “the Lifebuoy” A second GPU tier holding the deltas of entries just evicted from the hot cache. If one of them is selected again it is rebuilt on the GPU instead of being fetched over the link. reference setting “the Pin” One fixed rig used for every estimate: HiSparse’s GLM-5.1 deployment converted to 8-bit storage — 78 sparse layers, top-2048 selection, 100K-token context, 0.64 KB entries, 30 ms per token, a 50 GB/s link, 30 GB of GPU memory for KV. HiSparse “the Two-tier Library” The production system we build on. It keeps each request’s full KV history in host memory and a small least-recently-used hot cache of raw entries per layer on the GPU. Model outputs are unchanged. indexer “the Scout” A cheap scorer that, at every layer and every decode step, looks over all past positions and picks the k that attention will read. Its picks are announced before any KV bytes are touched. Lucky Louis property “the Gambler” From one decode step to the next, the indexer re-selects mostly the same positions, so a cache that bets on last round’s winners keeps winning. It is about WHICH entries are wanted, not about their bytes. neighbour similarity “the Neighbours” The family of hypotheses that an entry costs fewer bits to store exactly when a neighbouring entry (along some axis of the KV tensor) is already known. Members: fallen-apple (token axis) and upstairs (layer axis). fallen-apple similarity “the Apple” Hypothesis: an entry is cheaper to store exactly given an entry of the same layer a small token distance Δ away, and the closer the neighbour the cheaper. A curve over Δ, not a threshold. ‘The apple does not fall far from the tree.’ upstairs similarity “the Staircase” Hypothesis: the entry of the same token one layer up is partly predictable from the entry below it. Layers are the floors of a building; tokens run along each floor. cat-thread ladder “the Ladder” The intuitive argument for the project — an entry is less surprising against its thread than against everything, and least surprising against its own neighbourhood. Right in direction, leaky in its evidence, and harsh in its exchange rate. solo “the Hermit” Coding each entry by itself with one fixed, global, context-free code (per-channel histograms fit once on a calibration corpus). Worth about 1.1–1.3× on 8-bit KV. The baseline every dictionary must beat. loc “the Anchor” The lightest dictionary: for each channel, a typical value (location) and spread (scale). Predict each element by its channel’s location; store the exact difference. Costs about 2 entries’ worth, no per-entry tax. KLT “the Compass” The rotation of the axes that lines them up with the directions in which the data spreads most (the same thing as PCA). After it, the coordinates are uncorrelated and can be coded one by one with no loss of efficiency. VQ “the Hive” Describe each vector by the index of the nearest of C reference vectors (centroids) in a codebook. Losslessly, the index is a prediction and the exact residual is stored too; the index costs log2​C bits per vector. sib “the Twin” Use another entry of the same block (the nearest “sibling”) as the prediction, plus a pointer to it. Cheap side information, but the residual is the difference of two noisy vectors, so its noise doubles. global scope “the Globe” A dictionary fit once, offline, on a calibration corpus and shared by every request. Free at serving time; captures only what all texts have in common. request scope “the Thread” A dictionary fit on one request’s own history, loaded once when the request is admitted. Captures what is special about this conversation. block scope “the Brick” A dictionary per block of b tokens. Fits the local neighbourhood best, but there are many of them per request and they must be cached on the GPU. compressibility curve “the Arch” For one algorithm at one block size, the points (dictionary cost per entry, delta size per entry) it reaches as its settings vary. The lower envelope over all algorithms is the roofline the data allows.

Running themes

A handful of ideas come back again and again. Each time one does, a dashed card marks it and lists every other place it appears.

Predict, then store only the surprise Every lossless coder in this story has the same shape: guess the next thing from what both sides already know, then store only how wrong the guess was. The better the guess, the fewer bits. Side information at both ends A message gets cheaper when the receiver already knows something relevant — an almanac, a trained dictionary, a block's statistics sitting on the GPU. The catch is that the receiver must really have it. Pay once, use many times A fixed cost (a dictionary, a codebook, a calibration) is worth paying only when it is shared by enough items. Per item it costs (fixed cost) ÷ (number of items). The access pattern decides the form How data is read — one big stream, or many tiny scattered pieces — decides what a compressor is allowed to look like, before any statistics are considered. Which entries, versus what is inside them Knowing which items will be wanted (a property of the requests) is a different thing from the items being alike (a property of their bytes). Evidence for one is not evidence for the other. Bits are the unit Surprise, redundancy, mutual information and compressed size are all measured in bits, and bits × item size = bytes on a wire. Similarity scores that do not convert to bits do not count. Lossless pays for all the noise A lossless code must reproduce every last bit, including the parts that are pure noise. Whatever no predictor can explain sets a floor that no clever dictionary can go below. Every helper charges a tax Each piece of side information costs something to store or send: index bits, dictionary bytes, escape lists, flags. A method wins only if its gain is larger than its tax. Trust, but shuffle A measurement is believable only with controls that would expose a mistake: shuffled data where the effect must vanish, synthetic data with a known answer, and a real round trip that must be exact. The number grid is not neutral How numbers are stored (a uniform integer grid or a logarithmic floating-point grid) changes which tricks work. The same prediction can save bits on one grid and lose bits on another.
