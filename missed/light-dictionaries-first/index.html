VII.14

Light dictionaries first

A per-channel location-and-scale dictionary weighs about two entries. Kept on the GPU for every block of every request, it costs a few percent of the hot cache — and the hardest question of the design, which dictionaries to keep resident, goes away.

Two travellers set off through fifty countries. One carries a pocket phrasebook for each; together they fit in a coat pocket. The other carries one heavy encyclopaedia at a time, posting it home at every border and ordering the next. The second traveller knows more words. The first never has to plan.

kv-blockdiff faces the same choice for its dictionaries. A light one can travel with every block. A heavy one has to be fetched, cached and evicted — and that machinery is the hardest part of the design.

Back storyWhat the first draft did not see

It pictured heavy per-block dictionaries (codebooks of hundreds of centroids) and a dictionary cache with a residency policy at the heart of the system. Item 13 of the old list: a per-channel location/scale dictionary weighs w ≈ 2: it can be kept resident for every block of every request. Residency then stops mattering for lever 1.

How light is light?

ReminderWeight and amortization

A dictionary of dictionary weight w takes w entries’ worth of memory. Shared by a block of b entries, it costs 8w/b bits per element (VI.14 The amortization rule).

Line up the four dictionary types of Part VI at the block size wave 1 uses most, b = 2,048 tokens. A request of L = 100,000 tokens then has about 49 blocks per layer.

type weight w all blocks resident, per layer share of a 4,096-slot hot cache amortized, bits per element
loc (location + scale) 2 98 2.4 % 0.008
rank-16 basis (KLT) 32 1,563 38 % 0.13
256-centroid codebook (VQ) 256 12,500 305 % 1.0
full basis, d = 640 1,280 62,500 1,526 % 5.0

Notice the jump. The first row is a rounding error. The second already costs a third of the hot cache; the last two cost more than the hot cache itself.

Per request, across all NL​ = 78 layers of the reference setting, the loc row is about 4.9 MB, next to a 205 MB hot cache. Each block’s loc dictionary takes two slots’ worth of GPU memory. The old list said “smaller than one hot-cache slot per block”; with w ≈ 2 it is two, and the conclusion stands.

Takeaway
  • loc weighs about 2 entries; for every block of a 100K-token request it costs ~2.4 % of the hot cache.
  • A rank-16 basis already costs 38 %, a codebook three hot caches: heavy dictionaries cannot travel with every block.

Residency stops mattering

If every block’s dictionary is on the GPU, the dictionary cache has nothing to decide.

  • Every miss is a δ-miss: the δ-miss fraction is fD​ = 1.
  • No dictionaries are loaded during decoding: nload​ = 0.
  • There is no residency policy to design and no block-level trace replay to run for lever 1.

What remains is a clean trade: less link traffic per miss against a little more GPU memory per request. The figure prices it for every type at once.

ReminderRequests per GPU

A GPU serves N=min(Nlink​,NHBM​) requests: the link bound shrinks as each step moves more bytes, the memory bound as each request occupies more GPU memory (IV.15 What "better than HiSparse" means, VI.15 The economics, written out).

☞ Things to try
  1. At the defaults (b = 2,048, ρ = 0.75): loc reaches 143 requests per GPU against HiSparse’s 109 (1.31×), and is now limited by memory, not the link.
  2. The rank-16 basis lands at 106 — slightly worse than HiSparse. The 256-centroid codebook falls to 36.
  3. Set ρ = 0.85: loc still gains (129, 1.18×). Slide b down to 512: loc barely moves, while every heavier type collapses.
Running themePay once, use many times

At w ≈ 2 the fixed cost is so small that it hardly matters how many entries share it. For heavy dictionaries the same 8w/b decides everything — and keeping them for every block is out of reach.

Also on I.4 · II.24 · IV.3 · IV.5 · VI.6 · VI.14 · VII.4 · VIII.6 · VIII.7
Takeaway
  • With light dictionaries resident everywhere, fD​ = 1 and nload​ = 0: lever 1 needs no residency policy.
  • In the reference setting loc turns HiSparse’s 109 requests into ~143 at an assumed ρ = 0.75; the heavy types lose.

What changes in the plan

The default design becomes: light dictionaries, all resident. That means loc at block or request dictionary scope, possibly with a global basis (scope global costs nothing per request). Heavy dictionaries become a branch that only the data can open.

Light versus heavy dictionaries
Light (loc, a global basis)
  • Weight ≈ 2 per block; free at global scope.
  • Resident everywhere: fD​ = 1, no loads.
  • Catches drifting means and the few channels with large, slowly varying values.
Heavy (codebooks, per-block bases)
  • Weight 32–1,280 per block.
  • Must be cached and fetched: fD​ and nload​ depend on where misses land.
  • Worth it only if the data clusters (VII.13 Bounds before building).

Risks R4 and R7 of the plan (IX.15 Weak spots, risks and pivots) shrink accordingly. The question “do misses pile into a few heavy blocks?” (VIII.4 Q3: do misses concentrate in few, long-lived blocks?) still matters for the science, but lever 1 no longer waits for its answer.

Takeaway
  • Default: loc everywhere, always resident. Framework C runs only if wave 1 says the data needs heavy dictionaries.
  • All-resident light dictionaries are also what makes the victim tier possible (VII.16 A victim tier of deltas).
